# Architecture Decision Record

维护 `docs/adr/` 下的架构决策记录。

**规则正文在 `docs/adr/README.md`**，本文件只描述执行顺序。两者冲突时以 `docs/adr/README.md` 为准，并顺手修正本文件。

## 1. 判定是否需要 ADR

对照 `docs/adr/README.md` 的「何时需要新增 ADR」与排除条件。

**不属于必须记录的情况就明确说不需要写**，并指出该内容应该落在 `README.md`（当前行为）还是 `HANDOFF.md`（开发状态），然后结束——不要为了走流程而创建文件。

判断有分歧时说明理由，交给用户决定，不擅自创建。

## 2. 读现状

* 读 `docs/adr/README.md` 的索引表，取当前最大编号。
* 读与本次决策直接相关的 ADR 正文，判断是**新增**还是**取代**。
* 读 `docs/adr/template.md` 作为骨架。
* 不要通读全部 ADR。

## 3. 分配编号与文件名

* 文件名：`docs/adr/NNNN-<ascii-slug>.md`。
* 编号 = 当前最大编号 + 1，四位零填充，连续、**不复用、不跳号**。
* 一次任务通常只写一篇；同一个变更里出现两个独立决策时写两篇。

## 4. 写正文

按 `docs/adr/template.md` 的章节写。硬性要求：

* 「决策」用可检验的陈述句，不写"建议""可以考虑"。
* 「备选方案与取舍」至少列一条并写明否决原因。**列不出备选说明这不是一个决策**，应回到第 1 步重新判定。
* 「后果」必须写真实的已知缺口与限制，不许美化。
* 必须写「重新评估的触发条件」——可观察的推翻信号，不能写"视情况而定"。
* 头部填写状态、日期、来源提交。
* 「代码与测试」用 `path:line` 定位，**同时给出符号名**，因为行号会漂移。
* 不写当前参数值（那属于 `README.md`），不贴大段源码。

## 5. 处理取代关系

若本次决策推翻了已有 ADR：

1. **旧 ADR 只改状态行**：`Superseded by [NNNN](NNNN-slug.md)`。**正文一字不动**——决策的历史和被推翻的理由本身就是有价值的信息。
2. **新 ADR** 在「取代关系」中写明：取代日期、取代了哪一条结论、取代原因、哪些行为改变了、哪些保持不变。
3. **双向链接必须互相指向**。
4. **不删除旧文件、不改旧文件名、不复用旧编号**。
5. 旧 ADR 若在 `README.md` 有对应的当前行为描述，同步更新行为描述（README 只描述现状）。

## 6. 更新索引

更新 `docs/adr/README.md` 索引表：新增一行，或修改被取代行的状态列。

索引列固定为：编号 / 标题 / 状态 / 日期 / 来源。

## 7. 完成行为

* 不自动 commit。
* 回复用户：新增或取代了哪几篇（编号 + 标题 + 路径）、索引是否已更新、是否存在需要用户确认的判断分歧。
* 不在聊天中复制 ADR 正文，除非用户明确要求。
