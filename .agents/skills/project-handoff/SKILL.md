# Project Handoff

为当前代码项目生成一份可直接交给下一位 Agent / 新会话继续工作的 `HANDOFF.md`。

handoff 是**当前开发状态的可执行快照**，不是聊天摘要。只保留会影响后续开发的信息。

## 核心规则

1. 事实优先级：当前仓库实际状态 > 本次会话已验证事实 > 用户明确说明 > 推断。
2. 无法确认的内容写“未确认”，不要猜；聊天与仓库冲突时，以仓库为准并注明差异。
3. 严格区分“已完成 / 进行中 / 阻塞或未确认”。代码写出来但未验证，不算完成。
4. 待处理事项具体到文件 / 模块、动作和必要验证，避免“继续完善”之类空泛描述。
5. 不复制大段源码、diff、日志或聊天内容，不记录秘密值。
6. 默认只生成 handoff，不继续实现业务功能，不自动 commit，不修改无关文件。

## 执行流程

### 1. 确定项目根目录

- Git 仓库：使用 repository root。
- 非 Git 仓库：使用当前工作目录，并在 handoff 中注明。
- 输出固定为 `<project-root>/HANDOFF.md`，直接覆盖旧文件。

### 2. 提炼任务上下文

记录：

- 最终目标与当前子任务；
- 会影响后续实现的约束、设计决策及必要原因；
- 已明确不做的方向；
- 用户已经明确的下一步。

不要按聊天时间线复述讨论过程。

### 3. 检查仓库状态

环境允许时优先检查：

- 当前分支；
- `git status --short`；
- `git diff --stat`；
- 与当前任务有关的 unstaged / staged diff；
- 相关关键文件、类型、函数和最近 commit。

提炼“改了什么、为什么、是否完成或验证”，不要直接复制完整 diff。

### 4. 记录验证

只记录与当前任务相关的最新有效结果，例如测试、lint、type check、build、手工运行。

格式示例：

`pytest tests/test_provider.py -q` → 通过（12 passed）

如果代码后续又发生变化，使旧结果失效，标记“结果已过期，需要重新运行”。不要为了 handoff 无条件执行耗时很长的完整测试套件。

### 5. 写入 HANDOFF.md

严格使用以下结构：

```md
# Project Handoff

## 目标
- [最终目标]
- [当前子任务，如无可省略]

## 关键背景与决策
- [约束、设计选择、明确不做的方向]

## 当前状态

### 已完成
- [已实现且已确认的工作，若无写“无。”]

### 进行中
- [已开始但尚未闭环的工作，若无写“无。”]

### 阻塞 / 未确认
- [失败、未知、待决策、尚未验证，若无写“无。”]

## 验证
- `[命令或检查方式]` → [通过 / 失败 / 未运行 / 结果已过期]

## 待处理事项
- [当前仍未解决的问题、自然的后续工作或待决策项]
- 这些内容仅用于恢复上下文，不代表用户已经授权执行。

## 关键文件
- `path/to/file` — [为什么重要 / 当前改动点]

## 仓库状态与注意事项
- 分支：[branch / 未确认]
- 工作区：[clean / 有未提交修改 / 未确认]
- [不能覆盖的未提交工作、临时文件、兼容性风险等；若无写“无。”]
```

## 写作要求

- 使用简洁、事实性的中文；路径、符号名、命令、错误字符串、URL、API 名称和 identifier 保持原样。
- 只列接手当前任务真正需要的信息和关键文件。
- 不编造未执行的测试、未查看的文件或未确认的设计。
- 不重复 `AGENTS.md`、README 等文件里的长期规则。
- 多个方案尚未决定时，记录分歧，不替用户做决定。
- handoff 尽可能短，但不能隐藏失败、风险或未提交工作。

## Git 与完成行为

- 如果 `.gitignore` 已忽略 `HANDOFF.md`，保持现状。
- 如果未忽略，不擅自修改 `.gitignore`；最终回复中提醒用户它可能被 Git 跟踪。
- 不自动 commit handoff。
- 完成后只需告诉用户：`HANDOFF.md` 已生成或更新、文件路径，以及是否有关键未提交修改或验证失败。
- 不在聊天中再次完整复制 `HANDOFF.md`，除非用户明确要求。
