# Project Handoff

为当前代码项目生成一份可直接交给下一位 Agent / 新会话继续工作的 `<project-root>/HANDOFF.md`。

handoff 是**当前开发状态的可执行快照**，不是聊天摘要，也不是决策存档：

- 为什么这样决定、否决了什么，写在 `docs/adr/`；handoff 只引用编号，不复述理由。
- 当前行为是什么，写在 `README.md`；handoff 不重复。
- handoff 只写：现在做到哪、下一步在哪、什么还没确认。

## 核心规则

1. 事实优先级：当前仓库实际状态 > 本次会话已验证事实 > 用户明确说明 > 推断。
2. 无法确认的内容写“未确认”，不要猜；聊天与仓库冲突时，以仓库为准并注明差异。
3. 严格区分“已完成 / 进行中 / 阻塞或未确认”。代码写出来但未验证，不算完成。
4. 待处理事项具体到文件 / 模块、动作和必要验证，避免“继续完善”之类空泛描述。
5. 不复制大段源码、diff、日志或聊天内容，不记录秘密值。
6. 默认只生成 handoff，不继续实现业务功能，不自动 commit，不修改无关文件。
7. **增量演进**：可以覆盖文件，但不能覆盖语义。旧版本里的每一条信息都必须在新版本中有明确去向（保留、压缩、标注取代、归档），不得静默消失。
8. **先读后写**：更新模式下必须先读取现有 `HANDOFF.md`，再检查仓库状态。执行本技能视同用户已指定查看 `HANDOFF.md`。

## 执行流程

### 1. 确定项目根目录与更新模式

- Git 仓库：使用 repository root；非 Git 仓库：使用当前工作目录，并在 handoff 中注明。
- 输出固定为 `<project-root>/HANDOFF.md`。
- 判断模式：
  - 文件不存在 → **首次生成模式**。
  - 文件存在 → **更新模式**：先完整读取它，记下它记录的 HEAD、已完成条目、阻塞项和待处理事项。这些条目构成本轮必须逐一交代去向的**基线清单**。
- 旧文件结构与本模板不一致（历史版本）时，允许一次性重排结构，但必须把旧条目按语义分别迁入 已完成 / 阻塞 / 已归档，并在“更新于”行注明结构迁移。

### 2. 提炼任务上下文

记录：

- 最终目标与当前子任务；
- **仍然生效、且尚未写入 ADR** 的约束与决策；
- 已明确不做的方向（若已具备 ADR 条件，提示用户补充 ADR，而不是长期留在 handoff）；
- 用户已经明确的下一步。

不要按聊天时间线复述讨论过程。

### 3. 检查仓库状态

环境允许时优先检查：

- 当前分支；
- `git status --short`；
- `git diff --stat`；
- 与当前任务有关的 unstaged / staged diff；
- 相关关键文件、类型、函数和最近 commit；
- `docs/adr/README.md` 的索引表：只取仍然约束当前开发的编号与标题，**不读 ADR 正文**。

提炼“改了什么、为什么、是否完成或验证”，不要直接复制完整 diff。

### 4. 记录验证

只记录与当前任务相关的最新有效结果，例如测试、lint、type check、build、手工运行。

格式示例：

`pytest tests/test_provider.py -q` → 通过（12 passed）

- 保留最近一次有效结果与本轮新增结果；更早的结果折叠为一行 `- 更早：<命令> → 通过（<N> passed，结果已过期）`，不要静默删除。
- 代码后续发生变化使旧结果失效时，标注“结果已过期，需要重新运行”。
- 不要为了 handoff 无条件执行耗时很长的完整测试套件。

### 5. 增量合并（更新模式必做，首次生成模式跳过）

对基线清单逐条给出**一个明确去向**：

- 旧「已完成」条目 → 保留为累积里程碑（必要时压缩，或并入阶段归档）。
- 旧「进行中」条目 → 仍未闭环则保留并注明起点 commit；已闭环则移入「已完成」并补 commit。
- 旧「阻塞 / 未确认」条目 → 仍未解决则原样结转并加 `（结转自 <commit>）`；已解决则移入「已归档」并写明关闭依据；确认不再适用则同样移入「已归档」并写明原因。**不允许静默丢弃。**
- 旧「待处理事项」→ 同上处理；已被 ADR 覆盖的，改写为 `- 已由 ADR-XXXX 覆盖`。
- 旧「关键背景与决策」中被推翻的条目 → 标注取代，不删除。

判定不清的条目一律留在「阻塞 / 未确认」，不要擅自关闭。

### 6. 写入 HANDOFF.md

严格使用 `## 模板` 的结构；增量规则见 `## 增量演进规则`。

## 增量演进规则

### 已完成：累积里程碑，只增不删

- 格式固定：`- <阶段/主题> — <一句话交付> — <commit>`；未提交的写“未提交”。
- 本轮完成的条目追加在**最前面**（最近的在上）。
- 旧条目只能压缩，不能删除：
  - 只留一句话结果，删掉细节与验证过程（验证只保留最近一轮）。
  - 同类条目可合并为阶段归档：`- 阶段归档（<起始主题>→<结束主题>）— <一句话概括 N 个主题> — <首 commit>..<末 commit>`。
- 上限 15 条（含阶段归档）。达到上限时，把最早的连续 3 条以上合并为 1 条阶段归档，直到回到上限以内。
- **压缩后必须保留 commit**：commit 是接手者回溯的唯一入口，丢了它等于丢了这条里程碑。

### 关键背景与决策：决策归 ADR，handoff 只引用

- 只记录**尚未写入 ADR、但会影响后续实现**的临时约束。
- ADR 用引用行表示，只写编号与标题，不写理由：`- ADR-XXXX <标题>`。
- 决策被推翻时改写为 `- <旧结论> —— 已取代：<新结论>（ADR-XXXX / <commit>）`，旧条目至少保留一轮；当取代关系已完整记录在对应 ADR 的「取代关系」小节后，可压缩为 `- 已取代：<主题>（ADR-XXXX）`。
- 发现某条背景已具备 ADR 条件却还没有：写成 `- 待补 ADR：<主题>`，并在完成回复中提醒用户。

### 阻塞 / 未确认 与 待处理事项：必须结转

- 结转条目保留原始描述并标注 `（结转自 <commit>）`，不要因为“这轮没动”就删掉。
- 关闭条目移入「已归档」，写明关闭依据（commit / 命令结果 / 用户决定）。
- 「已归档」只保留最近两轮，更早的折叠为一行汇总。

## 模板

```md
# Project Handoff

- 更新于：`<HEAD>`（<commit 标题>）
- 上一版基线：`<上一版记录的 HEAD>`（<相对现在的差距，如“落后 2 个提交”>）/ 无（首次生成）
- 分支：`<branch>`

## 目标
- [最终目标]
- [当前子任务，如无可省略]

## 关键背景与决策
- [尚未写入 ADR、但会影响后续实现的约束或决策；若无写“无。”]
- ADR：
  - ADR-XXXX [仍然约束当前开发的决策标题]
- 已取代：[旧结论] —— 已由 [新结论] 取代（ADR-XXXX / `<commit>`）。

## 当前状态

### 已完成（累积里程碑，只增不删，可压缩）
- [主题] — [一句话交付] — `<commit>`
- 阶段归档（[起始主题]→[结束主题]）— [概括 N 个主题] — `<首 commit>`..`<末 commit>`

### 进行中
- [已开始但未闭环的工作 + 起点 commit + 当前卡点；若无写“无。”]

### 阻塞 / 未确认
- [旧条目原文]（结转自 `<commit>`）
- [本轮新增：失败、未知、待决策、尚未验证；若无写“无。”]

### 已归档（本轮关闭）
- [旧条目] → [关闭依据 / commit]（只保留最近两轮）

## 验证
- `[命令或检查方式]` → [通过 / 失败 / 未运行 / 结果已过期]
- 更早：`[命令]` → [结论，结果已过期]

## 待处理事项
- [当前仍未解决的问题、自然的后续工作或待决策项；无则写“无。”]
- 这些内容仅用于恢复上下文，不代表用户已经授权执行。

## 关键文件
- `path/to/file` — [为什么重要 / 当前改动点]

## 仓库状态与注意事项
- 工作区：[clean / 有未提交修改 / 未确认]
- [不能覆盖的未提交工作、临时文件、兼容性风险等；若无写“无。”]
```

## 写作要求

- 使用简洁、事实性的中文；路径、符号名、命令、错误字符串、URL、API 名称和 identifier 保持原样。
- 只列接手当前任务真正需要的信息和关键文件。
- 不编造未执行的测试、未查看的文件或未确认的设计。
- 不重复 `AGENTS.md`、`README.md` 里的长期规则，**也不复述 ADR 中的决策理由——只引用编号**。
- 多个方案尚未决定时，记录分歧，不替用户做决定。
- handoff 尽可能短，但不能隐藏失败、风险或未提交工作；也**不能为了变短而删掉旧的里程碑、结转项和归档项**。

## 自检清单（写入前逐条确认）

- [ ] 是否先读取了旧 `HANDOFF.md`，并给每条旧信息一个去向？
- [ ] 「已完成」是否只增不减？新增条目是否都带 commit？压缩后是否仍保留 commit？
- [ ] 旧「阻塞 / 未确认」的每一条，是否都出现在 已完成 / 阻塞 / 已归档 之一？
- [ ] 被取代的决策是否显式标注，而不是删除？
- [ ] 是否只以编号引用 ADR，而没有复述理由？
- [ ] 是否写明了 HEAD、上一版基线和工作区状态？

## Git 与完成行为

- 如果 `.gitignore` 已忽略 `HANDOFF.md`，保持现状。
- 如果未忽略，不擅自修改 `.gitignore`；最终回复中提醒用户它可能被 Git 跟踪。
- 不自动 commit handoff。
- 完成后告诉用户：`HANDOFF.md` 已生成或更新、文件路径、本轮相对上一版**新增 / 压缩 / 归档 / 结转**了哪些条目，以及是否有关键未提交修改或验证失败。
- 不在聊天中再次完整复制 `HANDOFF.md`，除非用户明确要求。
