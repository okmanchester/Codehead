# Development Workflow

## 核心原则

- 遵循当前用户要求和仓库中生效的项目级指令。
- 保护用户已有修改：不要覆盖、回滚、整理或误归因与当前任务无关的改动。
- 只读取理解当前任务所需的源码、测试、配置和文档，不为“完整了解项目”扫描整个仓库或历史记录。
- 做最小充分改动：不擅自扩大范围、增加依赖、重构邻近模块或引入没有明确必要性的抽象。
- 以当前代码、测试、运行结果和工作区状态作为主要事实依据；历史计划和旧文档只在确有需要时参考。
- 完成必须建立在实际执行的验证和最终 diff 上，不把计划中的检查写成已完成。

## 工作流

1. **确认现状**
   - 理解用户目标，并检查与任务相关的工作区状态和已有实现。
   - 识别哪些改动在本轮开始前已经存在，避免误覆盖或误归因。

2. **决定是否需要计划**
   - 局部、明确、易回滚的修改可直接实施。
   - 对多步骤、跨模块、存在歧义、兼容性要求、迁移风险或难以回滚的修改，先形成简短计划。
   - 如果仓库已有 ExecPlan、ADR 或其他流程规范，按仓库自己的约定执行；不要仅为了满足本 Skill 创建新的文档体系。

3. **实施最小充分改动**
   - 优先沿用现有模块边界、抽象和编码惯例。
   - 发现范围外问题时记录即可；除非它阻塞当前任务，否则不要顺手扩大修改。
   - 如果实施中发现影响面或风险显著增加，先重新评估范围和验证强度。

4. **验证**
   - 优先使用仓库已有的测试、lint、type-check、build 或其他原生验证入口。
   - 先运行直接覆盖本次改动的最小验证，再根据影响和风险扩大范围。
   - 修复缺陷时，尽量验证原始失败场景或等价回归用例。
   - 最后检查实际 diff，确认没有非预期修改、调试残留、生成物、密钥或用户已有改动被错误处理。
   - 无法在当前环境验证的部分必须明确说明。

5. **交付**
   - 基于实际 diff 和已执行的检查说明：改了什么、关键原因、验证了什么、还有什么未验证或受环境限制。
   - 只报告真实执行和观察到的结果；不要把“应该通过”写成“已通过”。

## 边界

- 仓库级长期事实、固定命令和团队约定应放在 `AGENTS.md`、README 或仓库自己的文档中，而不是复制到本 Skill。
- 专项流程（如数据库迁移、发布、benchmark 审核、安全审查）应优先使用独立 Skill 或仓库规范，而不是继续扩充本 Skill。
- Harness 已经可靠提供的能力（上下文管理、工具调度、权限、计划模式、subagent、checkpoint 等）由 Harness 负责；本 Skill 只保留跨 Harness 仍有价值的工程约束。
