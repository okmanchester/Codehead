# 0010. 恢复契约：只有正常退出的会话可恢复

- 状态：Accepted
- 日期：2026-09-23
- 来源：`6273528` 初步实现Session Resume, 正常退出后的会话续聊

## 背景

存档（见 [0008](0008-append-only-archive.md)）让历史能跨进程存活，但「能读到历史」不等于「能安全继续」。一个崩溃或被杀死的进程可能留下：未收尾的回合、已记录但无结果的工具调用。直接续聊会让模型看到一段自相矛盾的历史，并可能重复执行已经产生副作用的工具。

此外，同一个会话可能被两个进程同时尝试恢复。

## 决策

**把「可以恢复」定义为一个严格的、需要在同一事务内验证并占用的条件。**

### 只有正常退出的会话可恢复

会话有三种退出状态（数据库中以字符串 + CHECK 约束存储，**没有对应的 Python 枚举类型**）：

| 状态 | 含义 | 可恢复 |
| --- | --- | --- |
| `active` | 运行中，或未正常关闭 | 否 |
| `closed` | 在输入提示处正常退出 | **是** |
| `legacy` | 功能上线前的会话，退出状态未知 | 否（可列出） |

标记为 `closed` 的条件是**同时**满足：在输入提示处输入 `exit` / `quit`、收到 EOF 或按 Ctrl+C；没有运行中的回合；已记录的工具调用都有对应结果。模型错误、压缩失败、步数耗尽或已收尾的中断之后返回输入提示，仍可正常退出并在下次恢复。

数据库故障、无法确认工具停止、或进程异常退出**不会**写入正常退出标记，会话保留为 `active` 并拒绝恢复。**不提供强制解锁**。

### 占用与校验在同一事务内完成

`SQLiteSessionStore.restore` 的整个逻辑在**一个事务**里，且**第一条语句就是认领写入**（`UPDATE ... SET status='active' WHERE id=? AND status='closed'`），随后才读取元数据并做全部校验。

这样做的原因是避免「先读后写」的锁升级：两个进程同时尝试恢复同一会话时，先取到写锁的那个把状态改成 `active`，另一个的认领语句影响行数为 0，直接失败。校验失败时事务不提交，认领被回滚。

> 注意区分：连接初始化时的 `BEGIN IMMEDIATE` **只用于建表与迁移**，不是恢复机制的组成部分。

### 校验内容

- workspace 必须与当前一致（不支持跨 workspace 恢复）。
- 全部回合与工具执行必须已收尾。
- 消息序号必须是 `1..MAX` 连续无空洞。
- 检查点引用的保留序号必须有序、去重、以 1 开头；检查点之后不得有悬空消息。
- 消息与检查点必须能反序列化，结构损坏时**明确报错，不回退到旧检查点**。
- 检查点、消息格式或工具交互结构损坏时明确报错。

### 恢复后的语义

- 沿用原会话 ID、消息序号、摘要和**存档中的 system prompt**（包括当时的 `AGENTS.md`）。若与当前指令不同会提示；要采用新指令应新建会话。
- 只加载最新摘要、保留消息及检查点之后的新增消息，**不重新加载被压缩的原文**。
- 模型、端点、工具和输入预算使用**当前配置**；模型名与端点均相同时保留 token 校准系数，任一变化则重置为 1.2 并提示。
- 每个新回合重新计算 `max_steps`。
- **等待新的用户输入**：不自动继续上一轮、不自动重试模型请求、不重新执行历史工具。

### 生命周期 API

- `Session.finish()` — 调用方确认已正常退出且无执行中回合时调用，写入退出标记和校准系数。
- `Session.close()` / `store.close()` — **仅释放资源**，不写入正常退出标记。
- 已 `finish` 的实例不能继续追加消息；要继续必须通过恢复入口获得新实例。
- 旧数据库自动、事务性地增加恢复所需字段，原始消息与检查点保持不变。

## 备选方案与取舍

| 备选 | 为什么不采用 |
| --- | --- |
| 允许恢复 `active` 会话并尽力修复 | 「尽力修复」无法判断一个 `pending` 工具调用是否已经产生了副作用；重放或不重放都可能错 |
| 提供强制解锁标志 | 会把安全性判断外包给用户在压力下的临时决定，而故障原因恰恰是「无法确认状态」 |
| 在恢复后再做占用检查 | 读与写之间留出竞态窗口，两个进程可能都通过校验 |
| 回退到上一个完好的检查点 | 会让模型看到一段与实际会话不符的历史，且掩盖了存档损坏这一事实 |
| 恢复时沿用存档中的模型与端点 | 用户可能已经更换了模型或供应商；静默沿用会让人以为配置生效了 |
| 恢复后自动重试上一轮 | 上一轮可能就是失败原因（步数耗尽、模型错误），自动重试会形成循环 |

## 后果

- 崩溃后的会话**永久不可恢复**，即使历史完好。这是刻意的保守选择。
- 不支持 ID 前缀匹配、自动选择最近会话或跨 workspace 恢复；指定 ID 无效时报错而不新建会话。
- 恢复时输入预算与工具集使用当前配置，但 system prompt 来自存档——两者可能不一致，因此有提示机制。
- 空会话（正常退出且从未输入）也可恢复，首次输入使用当前 system prompt。

**重新评估的触发条件**：若需要崩溃恢复，前提是能可靠判定每个工具调用是否已产生副作用——当前不具备这个能力。届时应新增一篇 ADR 取代本篇，而不是放宽校验。
