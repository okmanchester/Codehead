# 0024. Unix Shell 使用 errexit 与 pipefail 暴露验证失败

- 状态：Accepted
- 日期：2026-10-20
- 来源：工作区变更；基于首轮三题轨迹的回归

## 背景

首轮 SWE-bench 的测试失败经过 `tail`、`grep`，或后续成功命令后返回 0，
导致工具成功状态被误读为验证成功。[0015](0015-tool-system-v1-freeze.md)
保留了 Shell 自身的退出状态，但未约定 Unix 复合命令的失败传播。
新增真实工具回归先在旧实现产生 5 项失败，随后验证修复。

## 决策

Unix 继续用 `/bin/bash -lc`，在登录初始化之后、用户命令之前执行
`set -e -o pipefail`。保留真实退出码，通过原有 ToolRuntime 返回失败和输出。
不解析测试日志推断成败，不启用 nounset，不更改 Windows PowerShell 的既有恢复语义。

## 备选与代价

- 仅启用 pipefail：仍会被后续成功命令覆盖，不能覆盖 Django 样本。
- 提示模型自行检查退出码：可作为后续实验，但不能修复工具默认产生的误报。
- 解析任意 Shell 或从错误文本推断状态：复杂且误判边界不可靠。

遵循 Bash 的 errexit 规则，条件、AND/OR 列表和显式恢复不保证遇到任意非零值就退出；
嵌套 Shell、子进程内部主动忽略错误也不在此保证范围。提前关闭读取端可能让上游因
SIGPIPE 返回 141，工具如实报错，不一律豁免。预期失败需显式处理。

重新评估条件：实际兼容性回归显示此默认值阻碍任务，或需要独立结构化验证工具。
本决策补充 0015，不改变其 Runtime、输出截断或生命周期契约。
