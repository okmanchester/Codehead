# 验证与证据

验证必须对应实际改动和风险。原则是：**先最小、最快、最相关，再逐步扩大；所有“通过”都必须来自真实执行。**

## 先发现仓库自己的验证方式

不要在 Workflow 中假设固定技术栈或命令。优先从当前仓库寻找真实入口，例如：

- `AGENTS.md` / `CONTRIBUTING.md` / README。
- `pyproject.toml`、`pytest.ini`、`tox.ini`、`requirements`。
- `package.json`、workspace 配置、lockfile。
- `Makefile`、`Taskfile`、`justfile`。
- CI workflow、build scripts、lint/type-check 配置。
- 仓库已有测试目录和邻近测试文件。

如果存在多套命令，选择与当前改动最直接的一套开始验证。

## 推荐验证顺序

1. **目标验证**
   - 运行直接覆盖本次改动的单元测试、集成测试、静态校验或最小复现。
   - 修 Bug 时优先确认能够覆盖原始失败场景。

2. **邻近验证**
   - 运行受影响模块或相关测试组。
   - 必要时执行 type check、lint、compile/build。

3. **仓库级验证**
   - 根据任务风险和仓库规模决定是否运行完整测试、完整构建或 CI 等价命令。
   - S 级任务不机械要求全仓测试；L 级任务通常需要更广验证。

4. **Diff 检查**
   - 查看 staged、unstaged 以及相对 `HEAD` 的实际 diff。
   - 确认没有范围外重构、调试代码、生成物、密钥或用户已有修改被误处理。
   - 适用时运行 `git diff --check`。

5. **无法自动验证的部分**
   - 对 UI、外部服务、真实凭据、硬件、人工交互等无法在当前环境验证的部分，明确写出缺少的条件和仍未验证的行为。

## 证据要求

- 只报告实际运行过的命令、退出状态和观察结果。
- 不把“应该通过”“预计没问题”写成验证完成。
- 不把测试数据集、eval corpus 或测试脚本的存在当作测试已经执行。
- 区分：本轮引入的失败、用户已有失败、环境限制、外部依赖问题和范围外问题。
- 如果某个检查失败但与本轮无关，保留事实并说明依据，不擅自顺手修复。
- 对用户已有 staged/unstaged 修改与本轮修改分别审阅，避免错误归因。

## 完成标准

任务是否完成由用户目标和风险决定，而不是由固定命令清单决定。通常至少应满足：

- 请求的行为已实现或问题已修复。
- 有与改动直接相关的验证证据。
- 实际 diff 与约定 scope 一致。
- 已知失败、未验证项和环境限制被明确报告。
