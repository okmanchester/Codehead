# 开发知识边界

不同来源承担不同职责。仓库不存在某类文档时，不要为了满足 Workflow 自动创建它；只有当信息确实需要长期保存时才引入相应载体。

## 权威顺序

通常按以下顺序判断当前事实：

1. 当前用户要求和当前 Git 工作区。
2. 当前源码、测试及实际运行结果。
3. 当前仓库指令与仍有效的架构/接口文档，例如 `AGENTS.md`、README、architecture docs。
4. 已接受的 Decision Records / ADR 中记录的长期理由与约束。
5. 与当前任务对应的 active ExecPlan，仅表示当前执行状态和计划。
6. completed plans、legacy docs、旧聊天记录或历史提案，只作为按需历史证据。

如果这些来源冲突，优先相信更高层级且可执行、可验证的当前事实，同时修正已经过时的长期文档。不要让计划中的“预期行为”覆盖源码和测试已经表现出的行为。

## 文档职责

### 当前架构文档

用于描述**现在仍然成立**的结构、边界、接口、关键约束和已知未实现能力。

不要把逐次开发过程、临时 TODO、完整调试记录塞入 architecture 文档。

### Decision Record / ADR

用于保存一个未来仍需要知道的、非显然且持久的设计决定，例如：

- 模块边界或依赖方向。
- 公开契约和兼容策略。
- 数据格式或迁移策略。
- 安全、可靠性、权限或执行语义上的长期约束。
- 多个合理方案之间的重要取舍。
- 已反复出现、需要长期防止回归的系统性问题。

普通 Bug 修复、测试补充、重命名、文案调整、局部重构、沿用既有抽象的实现通常不创建 ADR。

如果仓库已有 ADR 格式和状态规则，遵循仓库自己的规则。

### Active ExecPlan

保存复杂任务的执行状态，包括目标、范围、阶段、发现、决策和验证。

它是**执行记忆**，不是项目当前事实的最终来源。任务完成后不要继续把它当作默认上下文加载。

### Completed / Legacy History

用于追溯过去发生过什么，不默认代表现在仍然成立。

不要把整个 completed 或 legacy 目录批量加载到上下文中。

## 何时读取历史

只在有明确问题时读取最相关的单个或少量历史记录，例如：

- 继续尚未完成的 active plan。
- 当前源码、测试、架构文档或 ADR 之间出现冲突。
- 需要理解一个非显然设计理由或曾放弃的方案。
- 排查疑似历史回归。
- 用户明确要求追溯某次修改。

优先通过文件名、ID、`rg`、Git history 或仓库索引先定位，再读取正文；不要先扫描所有历史文档再寻找答案。

## 何时沉淀新知识

在任务结束前问三个问题：

1. **系统现在的事实变了吗？**
   - 是：更新当前架构/接口文档。
2. **产生了未来仍需遵守的非显然决策吗？**
   - 是：创建或更新 Decision Record。
3. **只是这次任务的实施过程吗？**
   - 是：留在 ExecPlan、Git history 或最终报告中，不提升为长期文档。
