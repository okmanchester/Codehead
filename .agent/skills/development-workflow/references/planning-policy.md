# 规划与任务分级

S / M / L 表示**当前这次修改的风险、影响范围、既有约束和恢复成本**，不是代码模块的重要程度，也不决定固定文档数量。

判断时重点考虑：

- 是否已有用户、调用方、测试、持久化数据或外部系统依赖当前行为。
- 是否改变公开接口、持久化格式、配置语义、执行语义或安全边界。
- 改动跨越多少模块，是否需要多个相互依赖的步骤。
- 出错后是否容易回滚，失败是否会造成数据、兼容性或运行时风险。
- 是否存在明显歧义，需要在实施过程中持续记录决策和发现。
- 是否可能跨会话、多人协作或长时间执行。

**不要仅凭模块名称升级任务。** 例如，greenfield 项目第一次实现一个简单 Agent Loop 通常可以是 M；而在已有稳定行为和测试契约的系统中重构同一个 Loop，可能是 L。

## S：局部低风险

典型特征：

- 边界清晰，影响局部。
- 不改变公开契约、持久化格式或长期架构。
- 修改容易理解、验证和回滚。

处理方式：

- 简短规划后直接实施。
- 不创建持久任务记录。
- 运行最相关的局部验证并检查 diff。

## M：普通功能或连贯跨文件改动

典型特征：

- 需要多个相关修改，但仍能由现有模块边界承载。
- 风险、影响和恢复成本中等。
- 可能新增一个能力、工具、流程或内部抽象，但没有高风险迁移或大范围契约变化。

处理方式：

- 先形成简洁的执行计划，再开始修改。
- 默认不创建持久记录。
- 只有任务存在多个里程碑、明显歧义、较高恢复成本、跨会话需求或用户明确要求时，才创建轻量 living ExecPlan。
- 遵循既有设计时不自动创建 Decision Record。

## L：高影响、难恢复或形成长期约束

典型特征包括但不限于：

- 修改已经稳定的架构边界、核心执行语义或安全边界。
- 改变公开 API、协议、配置语义、持久化格式，或需要迁移与兼容策略。
- 涉及多个模块的协调切换，局部失败可能留下不一致状态。
- 回滚成本高，或者需要分阶段发布、数据迁移、兼容窗口。
- 任务复杂到仅靠聊天上下文难以可靠恢复执行状态。

处理方式：

- 创建并维护一份 living ExecPlan。
- 执行期间持续记录 Progress、Decisions and discoveries、Validation。
- 形成持久决策时创建 Decision Record；当前系统结构变化时更新 architecture 类文档。
- 完成并验证后将 active plan 归档；放弃时记录原因和剩余影响。

## 重新分级

分级不是承诺。实施过程中如果发现：

- 实际影响比预期更小，可以降级并停止不必要的流程。
- 出现新的兼容性、数据、安全或恢复风险，应立即升级。
- 原任务需要扩大 scope，应先明确新增范围，而不是默默继续。

## ExecPlan 建议格式

如果仓库已有 ExecPlan 规范，优先遵循仓库规范。否则可使用单个 Markdown 文件，至少包含：

- `# Context`
- `# Goal`
- `# Non-goals`
- `# Scope and affected areas`
- `# Plan`
- `# Progress`
- `# Decisions and discoveries`
- `# Validation`
- `# Outcome and remaining work`

推荐将 active / completed 状态分开保存，但不要仅为了满足此 Skill 而给小型项目创建完整文档体系。
